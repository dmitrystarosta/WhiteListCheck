# BelyjSpisok.ru --- оптимизация сайта и PageSpeed

**Дата фиксации:** 22 августа 2026\
**Сайт:** https://belyjspisok.ru/\
**Проект:** «Белый список?»\
**Назначение документа:** зафиксировать выполненную оптимизацию сайта,
состояние графических ресурсов и результаты PageSpeed, чтобы следующие
доработки можно было продолжать без повторного расследования.

## 1. Что было сделано

Основная задача этого этапа --- уменьшить вес изображений и устранить
замечания PageSpeed Insights по доставке графики, не меняя визуальный
вид сайта.

### Скриншоты приложения

Для скриншотов Android были подготовлены уменьшенные WebP-варианты для
адаптивной загрузки.

Используется `srcset`/`sizes`, чтобы браузер не загружал исходный
скриншот 1080×1920 там, где изображение фактически показывается
значительно меньше.

В ходе оптимизации использовались, в частности, варианты:

-   `screen-1-540.webp`
-   `screen-1-720.webp`
-   исходный `screen-1-1080.webp`
-   аналогичные уменьшенные WebP-варианты для остальных скриншотов
    сайта.

После изменения PageSpeed перестал показывать прежнее существенное
предупреждение `Improve image delivery` для основной группы скриншотов.

### Изображение виджета

Исходный JPG виджета имел размер 700×293 и в PageSpeed отображался
примерно как 388×162.

Для него был подготовлен уменьшенный WebP-вариант:

-   `assets/widgets/whitelistcheck_widget-400.webp`

В актуальном тесте этот файл весит около **3 KiB**.

Ранее PageSpeed оценивал возможную экономию исходного
`whitelistcheck_widget.jpg` примерно в **81 KiB** на desktop. После
оптимизации это предупреждение исчезло.

### Бейджи магазинов

На сайте используются оптимизированные WebP-бейджи:

-   `assets/badges/rustore-320.webp` --- около **6 KiB**
-   `assets/badges/github-320.webp` --- около **4 KiB**

### Иконки

PageSpeed фиксирует использование оптимизированных WebP-иконок, в
частности:

-   `assets/icon-256.webp` --- около **7 KiB**
-   `assets/icon-144.webp` --- около **4 KiB**
-   `assets/icon-96.webp` --- около **2--3 KiB**

### SVG для состояний виджета

Используются небольшие SVG-файлы (примерно по 1 KiB):

-   `assets/widgets/widget-vpn.svg`
-   `assets/widgets/widget-whitelist.svg`
-   `assets/widgets/widget-normal.svg`
-   `assets/widgets/widget-nonet.svg`

## 2. Адаптивная загрузка изображений

Для основного скриншота PageSpeed видел конструкцию вида:

``` html
<img
  src="https://belyjspisok.ru/assets/screenshots/screen-1-1080.webp"
  srcset="assets/screenshots/screen-1-540.webp 540w, ..."
  sizes="(max-width: 900px) calc(100vw - 48px), 480px"
  width="1080"
  height="1920"
  fetchpriority="high">
```

Это важно сохранить при дальнейших изменениях: браузер должен получать
изображение подходящего разрешения, а не всегда исходник 1080 px.

## 3. Шрифты

Сайт использует локальные WOFF2-файлы Golos Text.

PageSpeed показывает четыре файла примерно по 17--18 KiB каждый,
включая:

-   Golos Text Regular
-   Golos Text Bold
-   Golos Text Black
-   ещё один используемый вариант Golos Text

Шрифты уже достаточно компактны; на этом этапе дополнительно не
оптимизировались.

сравнения следует делать новый прогон.

## 5. Оставшиеся предупреждения PageSpeed

### Render-blocking CSS

PageSpeed указывает:

-   `/styles.css?v=20260816-layoutfix3`
-   размер: около **7.4--7.5 KiB**
-   mobile duration в контрольном тесте: около **160 ms**
-   оценка потенциальной экономии критического пути: до **450 ms**

Решено **не усложнять загрузку CSS** выделением critical CSS/асинхронной
схемой. Файл очень небольшой, а риск нарушить уже настроенную адаптивную
вёрстку выше практической выгоды.

### Cache lifetimes

PageSpeed показывает короткий Cache TTL --- около **10 минут** --- для
собственных статических ресурсов `belyjspisok.ru`.

На mobile в отчёте было около **140 KiB** first-party ресурсов с
коротким TTL, на desktop --- около **168 KiB**.

В эту группу входят:

-   WebP-скриншоты;
-   Golos Text WOFF2;
-   `styles.css`;
-   иконки;
-   бейджи;
-   `script.js`;
-   SVG виджетов.

Сайт размещён на **GitHub Pages**, поэтому обычным `.htaccess` задать
длительные `Cache-Control` для этих файлов нельзя. На данном этапе это
предупреждение принято как инфраструктурное ограничение и специально не
исправляется.

CSS и JS уже имеют query-string версии, например:

-   `styles.css?v=20260816-layoutfix3`
-   `script.js?v=sliderarrows3`

Версионирование необходимо сохранять при будущих изменениях файлов.

### Яндекс.Метрика и кэш

PageSpeed показывает около **90 KiB** ресурсов Яндекс.Метрики.

Основной `mc.yandex.ru/metrika/tag.js` весит около **88 KiB** и имеет
TTL около **1 часа**. Некоторые служебные запросы Метрики не имеют
браузерного кэша.

Это сторонние ресурсы, их Cache-Control сайт `belyjspisok.ru` не
контролирует. Специальных изменений ради этого предупреждения не
требуется.

### Forced reflow

Контрольный отчёт:

-   Яндекс.Метрика `metrika/tag.js` --- **112 ms**
-   собственный `script.js?v=sliderarrows3` --- **7 ms**

Основная часть forced reflow создаётся сторонним скриптом Метрики.

Собственные **7 ms** признаны несущественными; менять логику слайдера
ради этого показателя не требуется.

## 6. Что НЕ следует переделывать без причины

При следующей оптимизации не нужно автоматически:

-   заново пережимать уже подготовленные WebP;
-   заменять локальные WOFF2 только ради PageSpeed;
-   встраивать весь CSS в HTML;
-   разбивать небольшой `styles.css` на critical/non-critical CSS только
    ради исчезновения предупреждения;
-   переписывать слайдер из-за 7 ms forced reflow;
-   пытаться исправлять TTL ресурсов Яндекс.Метрики;
-   считать единичный desktop `NO_LCP` доказательством проблемы сайта.

Сначала следует сделать новый PageSpeed-тест и сравнить реальные
показатели.

## 7. Текущее состояние и следующий разумный этап

После оптимизации изображений сайт находится в хорошем состоянии:

-   SEO --- 100;
-   Accessibility --- 100;
-   мобильный Performance --- 87;
-   CLS отсутствует;
-   TBT низкий;
-   основные неоптимизированные изображения устранены.

Оставшиеся замечания в значительной степени связаны с GitHub Pages,
обычным render-blocking поведением небольшого CSS и Яндекс.Метрикой.

**Приоритет следующего этапа --- функциональные, контентные и
SEO-доработки сайта, а не попытка любой ценой получить 100 баллов
Performance.**
